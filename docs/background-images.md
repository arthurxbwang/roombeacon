# 背景原图上传与屏幕比例预览

2026-10-10；本地修复与验证，尚未发布到生产。

## 原因与结果

旧后台允许选择 JPEG／WebP，但浏览器会先强制转成 PNG，再按 Base64 长度限制上传。用户提供的 2752×1536 JPEG 原文件为 1,760,654 字节，Chromium 转成 PNG 后为 6,328,534 字节，超过原有约 3 MB 限制；错误发生在发送请求之前。

新后台直接读取并上传原文件，服务端识别真实格式、检查容器完整性并实际解码，原始字节、格式和画质保持。支持静态 PNG、JPEG、WebP，单张不超过 3,000,000 字节（十进制 3 MB），宽高均不超过 4096 像素；动画、其他格式、损坏或截断图片拒绝。界面显示格式、实际 MB／字节数及显示像素尺寸，超过限制时说明当前原文件大小，不再提示转换后的 PNG 大小。JPEG／PNG／WebP 的 EXIF 方向影响显示尺寸时，元数据按浏览器看到的方向标注，不改写原图。

原图本地隔离接口上传和读取均返回 200，读回仍为 `image/jpeg`、1,760,654 字节，逐字节与附件一致；不代表生产或实机已经验收。

## 如何选择背景与比例

1. 在软件模板草稿中上传白天／夜间背景。上传期间暂不能保存草稿；可以取消编辑。失败时保留原背景，切换模板会取消旧上传，不把图片写到另一个草稿。
2. 使用“背景预览比例”检查裁切效果：新机常见为 16:9，旧款 10.1 寸为 16:10；另有两种竖屏比例。设备已上报网页宽高时，可直接选其短码和实际尺寸。没有上报的设备不猜测比例。
3. “等比铺满 · 居中裁切”按门牌实际显示框等比缩放，超出部分居中裁切；“完整显示 · 等比留白”保留整张图，比例不同时留边。两种方式都不拉伸变形，也不重新编码原图。切换预览比例不会永久裁掉原图或修改设备配置。
4. 保存草稿、发布软件版本，再在设备台账显式部署，核对目标设备的配置回执。仅上传背景不会自动替换已部署设备的背景。

比例缩略图用于检查背景。现有完整草稿预览仍是内容预览，其布局受后台浏览器尺寸影响，不能当作实机像素级验收。门牌保持原有背景透明度与内容层次。

## 接口与兼容

保留 `POST /api/v6/admin/assets` 的 `name`、`data` 字段，`data` 仍为 Base64，长度上限仍为 4,000,000 字符。响应保留 `id`，增加 `mime`、`size`、`width`、`height`。资源继续以原始文件 SHA-256 标识，SQLite 表结构、软件模板背景 ID、`background_fit=cover|contain` 均保持。

新增 `GET /api/v6/admin/assets/{id}`，供已登录管理员／只读账号读取背景名称、格式、大小和尺寸，重新编辑时也能显示信息。图片本体仍通过 `/api/v6/assets/{id}` 读取；设备只能读取其已部署背景，管理员写入继续检查角色、来源及 CSRF。不能根据扩展名或客户端 MIME 判断服务端格式。

旧 PNG 的读取权限、ID 和元数据兼容原 chunk／CRC 契约，不要求迁移旧资源。验证库固定为 `Pillow==12.3.0`，发布时需要安装更新后的后端依赖；版本来源为 [Pillow 官方 PyPI](https://pypi.org/project/pillow/12.3.0/)。

## 发布、回退与验证

本次只修改后端与 H5。Android 外壳从服务器加载网页，已有实际网页尺寸上报和同源图片加载能力；正式 APK 0.7.1／WebView 106 无需修改。发布仍须另行明确准确 Git SHA、目标服务器和备份，先更新后端依赖与代码，再验证新 H5，核对实际图片与两款门牌的裁切、可读性及配置回执；浏览器回归不能替代实机验证。

回退优先恢复原软件版本组合并核对回执；应用回退保留 SQLite 中的账号、设备、模板版本和新增资源，不整库覆盖。旧后端的资源读取使用数据库 MIME，可继续展示已上传 JPEG／WebP；回退后旧上传页恢复原 PNG 转换限制，新增元数据接口也随新应用回退。

新增后端回归覆盖三格式原始字节、真实类型识别、EXIF、大小／像素边界、损坏／截断／动画拒绝、旧 PNG 与权限；浏览器回归覆盖上传、元数据回载、失败保留、卸载取消、草稿保存和切换竞态、设备比例，以及 V6／V7 横竖屏的铺满／完整显示。验证结果见本轮 CHANGELOG；所有业务接口测试均使用隔离数据，不操作真实预约或生产配置。

本轮结果：679 项后端、199 项 Chromium 全量通过，无跳过；最终预览排版调整后 17 项背景定向复核通过。Ruff 0.16.7、npm ci、类型检查、隔离构建和 diff 检查通过。后端只有既有 TestClient 上游弃用提示。验证临时目录使用仓库 `output/background-validation`，避免本机 `/tmp` tmpfs 空间不足；Redis 使用本地临时 Unix socket，浏览器 API 使用明确的 fixture。

本地证据位于 `output/background-validation/original-api-proof.json`（真实本地后端、独立数据库）、`original-browser-proof.json`（原图浏览器上传、fixture API）、`upload-original.jpg` 及两款比例的 `display-original-16-9.jpg`／`display-original-16-10.jpg`。这些生成文件不进入源码提交，生产和实机仍待发布后验证。
