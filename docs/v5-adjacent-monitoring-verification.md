# V5 连续预约提前监控修复

日期：2026-09-20。目标：仅在既有 Control 服务器及 IT灯塔-Test 测试房间修复连续预约漏监控；其他房间维持官方方案。

## 原因和行为

旧版仅监控当前展示目标，前场保留至结束会让后场错过开始前登记。新版将展示目标与提前监控集合分离；平板显式确认本房间集合，服务器为每次预约分别保活。前场已签到、未签到、受保护均不妨碍后场进入监控窗口。当前确认提交不确认或中断下一场；异常、断线、会话变化、过期、重启继续保护相应预约。

不改变非重复预约登记要求、房间写入白名单、原生策略核对、释放等待时间或发出前核验。重复日程释放仍待单独开发验证。

## 隔离验证

- 新回归先在旧代码复现缺少后场监控；修复后覆盖前场三种状态、切场前后持续保活、前场正常确认、离线/异常/会话变更/重启/漏报、跨房间/删除/改期/重叠/窗口外拒绝、旧页面兼容。
- 模拟完整流程：前场已确认且保留，后场开始前登记、管理员登记非重复，超时等待60秒、平板挑战核验、飞书前置与结果查询，只向后场发送一次 NOT_CHECK_IN，之后的预约保留。
- 慢外部核验跨越下一场开始时间时，不得用旧时间登记为已提前监控。
- 前端：npm ci、类型检查/构建、70项Chromium测试通过，包含心跳显式覆盖前后两场而确认仅提交当前场。
- Python：168项测试、Ruff通过；所有飞书写入测试均为mock，不能作为真实释放验收。
