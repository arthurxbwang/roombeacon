# 开始后新增预约的签到与释放（#61）

2026-10-10。用户确认修复规则并授权开发、推送和上线；需求为 [#61](https://github.com/arthurxbwang/roombeacon/issues/61)。

## 原因与业务规则

原实现只有在开始前登记的预约才能进入自动释放流程。开始后首次发现的预约被标记为 `blocked / missed_window`；超过“开始＋宽限”后又不能签到，造成未签到仍一直占用。不能仅删除保护判断，否则重启、断网或记录丢失后可能误释放旧会议。

| 场景 | 本次规则 |
|---|---|
| 正常开始前进入监控 | 会前开放，截止为开始＋模板宽限；当前正式模板为 5＋5 分钟 |
| 连续健康监控中有充分证据的新预约，首次发现已开始 | 截止为首次可靠发现＋模板宽限，当前为 5 分钟；不超过会议结束 |
| 刚出现时尚未开始 | 截止仍为开始＋模板宽限 |
| 第一次采集、服务重启、断网恢复、查询范围扩大或证据不完整 | 不自动补授释放资格 |
| 已存在的保护记录、记录丢失但仍有已见标记 | 保持保护，不重新激活 |
| 改期形成新的时间实例 | 独立核验和签到，旧签到不继承 |

保护且无法签到的 V7 门牌显示“未签到，请联系管理员”。正常窗口内仍显示签到倒计时；前端统一使用服务器期限，刷新不延期。当前补签到仍为 0 秒；到期后先核验再释放，不保证整点零延迟，也不将核验失败误报为空闲。

## 新预约证据与持久化

当前忙闲缓存没有可靠的预约创建时间。实现证明的是“预约在持续观察中新增或改期出现”，不声称读取到了飞书创建时间。

中央采集及释放后的完整忙闲读回增加可选 `query_start`／`query_end`，记录实际查询范围。连续两份新鲜、完整、时间向前的快照必须都完整覆盖预约时段，且前一份没有、后一份有该实例。同时要求同一 worker 代际、策略版本、设备身份和页面会话，工作循环间隔小于 45 秒、真实心跳健康。缓存失效、重叠、读取异常立即断开观察链；恢复后的第一份快照只建立基线。旧快照没有查询范围时不能用于授予新增资格。

证据保存在兼容的 `rooms:usage:v1:observation:<room_id>` 和 `rooms:usage:v1:arrival:<occurrence_id>`。新增证据使用 NX 一次写入，保留首次发现和截止；删除后再次出现、刷新和重启均不能重置。新预约仍等待覆盖其自身的页面心跳，等待不延后期限。已有记录使用原有 Redis 键，新增可选 `admission`／`first_observed_at` 字段；仍保留原有 7 天记录期限，策略和暂停的持久保存方式不变。

签到接口、日历自动核验和超时 worker 使用同一份持久截止时间。来源日历映射、逐实例核验、房间白名单、真实终端回执、重复单实例释放、发送前重新查询、单次写入和释放后真实读回继续生效。新证据本身不等于释放授权。
