# 按预约定位日历来源（#2，2026-10-10）

修复分支 `codex/2-calendar-source-qualification`，基于已包含 #61 的 main `ed90c9f`。本次修复固定来源查另一组织者预约时持续 404／193001 的缺陷。[PR #64](https://github.com/arthurxbwang/roombeacon/pull/64) 已合并，用户授权后上线准确应用 `3a527ef`，仅IT灯塔-Test启用新来源解析；两场历史失败预约真实只读核验通过，见[生产回执](production-calendar-source-2026-10-10.md)。正式放行仍须完成[真实矩阵与72小时观察](../plan/calendar-source-release-readiness.md)。

## 行为与兼容

- 中央采集将组织者 open_id 按原有预约 identity 存入私有 `rooms:usage:v1:sources:<room_id>`，与公共 `rooms:snapshot:<room_id>` 用同一 Lua 操作发布，TTL 相同。较旧查询不能覆盖新来源；公共日程不增加人员或原始日历 ID。
- 房间位于 `ROOM_DISPLAY_USAGE_ORGANIZER_SOURCE_ROOM_IDS` 且位于原释放白名单时，按真实组织者批量查询主日历，再读取本场日程。`ROOM_DISPLAY_USAGE_AUTO_VERIFY_CALENDARS` 继续作为有依据的补充候选；未启用新配置的房间沿用旧路径。两者都不代替写入开关、策略、心跳和逐实例资格。
- 主日历只作候选，核对返回的 `organizer_calendar_id` 并跟到权威日历，最多3次读取；检查身份、状态、起止、重复与例外实例。多来源冲突、循环、缺字段、缓存失效和重叠实例全部拒绝授权。固定候选与主日历指向同一权威来源时合并。
- 私有核验依据保存为预约记录的 `_calendar_source`，包含版本2、应用／配置摘要、组织者及权威日历。对外过滤私有字段。发送前重新读取已核验的日历，并核对实时忙闲组织者，来源变化时保留预约，不能静默换日历发送。
- 旧自动核验记录继续按旧固定映射二次验证；人工登记流程保持。新增字段与旧 API 兼容，不重写预约 identity 或已有截止时间，不清除 confirmed、blocked、uncertain。

## 请求边界和诊断

每个 worker 客户端按应用 ID／凭证隔离缓存，主日历成功缓存300秒、缺失30秒，404日程组合缓存30秒；缓存最多512项，主日历批次最多50人并用锁合并并发。已缓存主日历失效时刷新一次，仅尝试新的有依据来源。发送前绕过日程负缓存，重新读取原来源。每次核验总预算8秒、单次日历HTTP请求4秒，资格查询重试不得越过本实例截止。

失败保留稳定原因、HTTP状态和数字业务码，不存上游正文／凭证。退避为30、60、120秒，上游数字 `Retry-After` 优先（最多一天）；相同错误合并审计、累计次数。429、403、5xx的非JSON网关响应也保留HTTP分类。成功证据才清除核验错误。截止时核验失败标为 `calendar_verification_failed`，不再伪装成开关未启用。

已认证的房间规则接口新增最近24小时未解决问题列表，最多检查10场，已签到／恢复的不再列出。中控分别展示房间开关、本次核验、失败原因和处理建议，每10秒刷新；保留未保存草稿，关闭窗口时停止计时器并取消请求。只读账号可查看，无修改权限。

组织者缺失、应用创建／共享／代订／私密预约只有存在可读取且权威一致的来源才会通过。此实现不能证明这些真实来源类型都已支持，正式使用范围须逐项验收。

## 候选发布与回退

1. 先完成PR审核，记录候选准确SHA及该SHA的测试回执。发布仅限已授权的 `roombeacon.thundersoft.com`／`/data/roombeacon`，从GitHub获取源码；本文件不授权部署。
2. 在发布窗口保存当前准确运行SHA、私有环境配置、策略／暂停及记录备份，暂停释放并确认无在途请求。只对测试房间设置新来源房间列表；保留原固定映射及房间白名单，核对新进程实际解析值和完整采集来源证据。
3. 用至少3位真实员工各2场新预约验证签到保留／未签到释放、实际组织者来源、日志分类与门牌一致；再覆盖正式范围内共享／代订／应用创建／私密和重复／改期。预约创建、邀请和真实释放须另行授权。截止后30秒内读回及72小时观察按原计划留证。
4. 配置回退先暂停释放，再撤去新来源房间列表；新版本会拒绝来源版本2记录失配后的发送。旧保护不重置，截止已过的预约不补发。
5. 应用回退到不认识私有来源依据的旧SHA时，必须保持服务器写入关闭并暂停，等待／逐项处置新版未结束实例后才能恢复旧固定来源流程。不能只切旧包就恢复写入，不能删除记录制造新资格；来源证据可按TTL自然过期。
