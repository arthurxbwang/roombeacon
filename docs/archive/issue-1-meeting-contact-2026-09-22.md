# Issue #1：会议联系人分析与暂缓决定

归档日期：2026-09-22。关联 [Issue #1](https://github.com/arthurxbwang/roombeacon/issues/1)。

## 决定与实际实现边界

用户确认保留显示规则：**联系人优先 → 可确认的组织者兜底 → 信息不可见**。当前影响有限，不是核心交付卡点；本 Issue 按 `not_planned` 关闭，表示接受现有限制、暂不继续实施，不表示联系人读取功能已完成或真实验收通过。

当前业务仍从忙闲响应取得组织者，必要时查询通讯录补全；前端显示“组织者”，缺失时为“信息不可见”。本次没有新增联系人采集、身份来源字段、前端切换或生产部署，也没有增加飞书授权。未来实现联系人优先时必须保留来源语义，不能把已有组织者字段改称已验证的联系人。

后续维护先读本文；在没有新增读取条件或业务优先级变化时，不重复开展同一轮接口搜索、权限扩张或身份猜测。

## 已确认的规则

1. 有按当前房间、当前预约准确匹配且可确认姓名的联系人时优先使用。
2. 联系人缺失或不可读时，可用该预约可确认的组织者姓名兜底。
3. 两者均不可确认时显示“信息不可见”，不猜测姓名。
4. 不以候选人、任意参会人、视频会议主持人、机器人名称或房间管理联系人代替预约联系人。
5. 不把一个共享异常组织者 ID 固定映射为某个人；不能按“面试”关键词硬编码姓名。
6. 姓名读取失败不改变忙闲时间、签到或释放规则；成功补全姓名也不自动扩大主题可见性。

## 普通会议的日历定位与权限实测

- 应用日历列表200/code0，仅返回应用自己的主日历；在该日历查询用户的测试预约返回404/193001。
- 通过 `POST /calendar/v4/calendars/primarys` 查询本次组织者的主日历成功，随后查询日历元信息成功；应用对其角色为 `free_busy_reader`。
- 在该主日历查询同一测试预约，`need_attendee=false` 返回200/code0；切换为 `need_attendee=true` 返回403/194001，未取得会议室参与者及 `operate_id`。
- 因此“能找到日历”“能读取基本日程”“能读取参与者”是三项独立证据。不能声称只要加一个API权限或日历reader就必然读取所有参与者；还要符合参与者可见性条件。
- 上述日历定位只对普通测试预约完成。面试系列的实际组织日历和创建应用仍未确认，不能套用普通样本的日历。

## 九类官方接口核查结论

2026-09-22核对官方文档；真实调用限已有授权下的只读查询，没有为查证主动创建预约、修改日历、申请权限或读取视频会议内容。

| 接口 | 与联系人相关的结论 |
|---|---|
| [会议室忙闲](https://open.feishu.cn/document/ukTMukTMukTM/uIDOyUjLygjM14iM4ITN) | `organizer_info.name/open_id` 为组织者。文档明确应用身份创建的日程不返回组织者姓名，私密日程不返回组织者信息。实际9条无联系人字段。 |
| [会议室主题和详情](https://open.feishu.cn/document/ukTMukTMukTM/uIjM5UjLyITO14iMykTN/) | 实际字段为 `uid`、`original_time`、`summary`、`vchat.vc_type/meeting_url`，没有联系人。 |
| [获取日程](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/calendar-v4/calendar-event/get) | 支持请求参与者，房间参与者中有 `operate_id`；`event_organizer` 是另外一种身份。已实测参与者请求受限。 |
| [日程参与人列表](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/calendar-v4/calendar-event-attendee/list) | 有 `operate_id`。文档要求日历reader/writer/owner、相应API权限及参与者查看条件；应用身份还需机器人能力。须按room_id匹配并处理分页。 |
| [添加日程参与人](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/calendar-v4/calendar-event-attendee/create) | 用于核对字段语义，未调用写入。应用创建预约时 `operate_id` 指定会议室联系人，在会议室信息中展示。 |
| [日历忙闲](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/calendar-v4/freebusy/list) | 返回忙闲开始、结束和RSVP状态，没有联系人，不能替代参与人接口。 |
| [视频会议预约](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/vc-v1/reserve/get) | 有 `reserve_user_id`，但语义是视频会议预约人，且有预约归属限制；未证明等于房间联系人。 |
| [视频会议详情](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/vc-v1/meeting/get) | 有主持人、参会人员，存在会议归属和时间范围限制；这些身份不是房间联系人。 |
| [会议室详情](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/vc-v1/room/get) | `room_status.contact_ids` 属于房间状态配置，不是逐场预约字段，不能用于推断预定者。 |

结论：不能说“飞书没有联系人接口”，也不能说“现有忙闲加主题接口已经足够”。已确认的候选是日历会议室参与者 `operate_id`，但本次未取得目标样本的真实联系人值。

## 影响范围与尚未确认的事实

- 北京当日110条样本中，没有发现标题不含面试关键词的缺姓名预约；101条有姓名不等于101条均已验证联系人。
- 此限制按创建身份和可见性决定，不按会议主题决定。其他应用创建的培训、评审等日程同样可能缺组织者姓名；普通员工的私密日程也可能不返回组织者。
- 通讯录范围、无效ID或跨应用身份对应也可能阻止姓名补全。现有缓存按App ID隔离，成功300秒、失败60秒，不使用过期姓名伪造结果。
- 应用/服务身份是有依据的排查方向，但具体创建应用、异常ID归属尚未确认；不将其记录为某位员工离职、账号损坏或某个已识别机器人。
- 原始组织者姓名为空会影响现有主题显示策略；本次主题接口查询成功不代表已允许修改线上主题可见性。

## 何时重开及如何接续

仅在用户重新提高优先级，或出现以下新增条件时再评估重开：取得目标组织日历及合法读取条件；源预约系统可提供按预约关联的联系人数据；官方提供新的适用接口或改变读取边界；缺姓名影响显著扩大。

接续顺序：

1. 复用本文结论，先定位实际创建应用和组织日历，或评估源系统按预约同步联系人。不要从重复申请通讯录权限开始，也不默认要求全员个人日历开放。
2. 用获授权的普通会议、应用会议及“同一组织者ID对应不同联系人”的样本做字段对照，证明单场匹配关系；不按房间或异常ID永久绑定人员。
3. 如实施，单独设计联系人来源与回退、缺失/不可读/无效ID、分页、多房间、重复/改期、缓存和跨应用边界的回归，保留既有API和鉴权兼容。
4. 验证姓名来源和界面语义后再评估部署。当前Issue关闭不授予未来日历扩权、源码发布或预约操作权限。
