## GitHub 开发方式

1. 一个明确需求对应一个 Issue，写明现状、范围、验收条件和部署边界；总规划只引用 Issue，避免维护多份相互冲突的进度。
2. 从最新 `main` 建 `codex/<issue>-<topic>` 短期分支，任务引用 Issue 与准确基线。并行任务使用独立工作树，避免同时改同一开发目录。
3. 先修复回归用例，再改业务实现；执行受影响组件的规范检查。纯文档整理做链接、敏感信息和 diff 检查，不将旧测试冒充本轮重新执行。
4. 提交并发起 PR，描述最终行为、测试和限制；引用 Issue。审阅及检查通过后合入 `main`，清理已合并分支与临时工作树。
5. 发布单独记录前后端准确 SHA、目标、配置变化、验证和回退。GitHub 合并不自动代表服务器已部署，也不自动扩大飞书写入或样机操作范围。
6. 每个任务结束前更新仓库文档和 Issue。新任务先读[当前状态](../docs/current-state.md)与本计划，不要求重新阅读所有历史对话。

本次用户授权包含建立标签、整理文档和 Issues、合并本次整理 PR、清理已合并历史分支及工作树、归档旧任务。它不意味着未来每个功能、生产发布或真实预约操作都已自动获得执行授权。

## 延续的约定

- 保持既有 API、环境变量、Redis 键和浏览器绑定兼容。
- 失联、过期、撤销、核验不明和传感器异常不能误报空闲或签到成功。
- 不回写 Argus 门牌副本，不默认部署旧服务器。
- VM 备份、指标采集及证书续期沿用既有责任约定，不重复开无效待办。
- 硬件资料从[开发资料索引](../docs/reference/README.md)按需读取：RK3568 使用 SDK 摘要，DP72 实施先读评估与勘误，再查协议原文。
