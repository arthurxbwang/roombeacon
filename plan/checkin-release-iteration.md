# RoomBeacon 确认使用与超时释放迭代计划

> 2026-09-20 方案修订：后续实施以 [V4 官方签到与 V5 保护释放计划](v5-protected-release.md)为准。V4 完全走官方渠道；V5 房间关闭原生未签到释放，由平板与服务器管理。新增操作异常保护及待释放核验已本地实现，通过隔离测试；虚拟房间真实释放尚未验收。下文为前一轮设计与接口调查，不作为最新试点安排。

更新：2026-09-20。用户批准以 V5 实施。本地代码已实现确认、观察与受控释放，真实 P0 验收及 P3 灰度尚未执行；未改动飞书预约、权限或服务器配置。实际实现与验证见 [V5 说明](../docs/v5-usage-verification.md)。下文保留原规划，实际差异以说明为准。

## 1. 版本目标与范围

本次功能版本确定为 Web V5「确认使用与会议室释放」。默认仍为 V4，APK 版本及软件发布号独立管理。

目标：参会人在门牌确认使用后保留本次预约；超时未确认时，由服务端调用飞书公开接口释放对应会议室。确认记录属于 RoomBeacon，不宣称已完成飞书原生签到。

首版包含：

- 门牌「确认使用」、确认截止时间、处理结果和异常状态。
- 服务器持久保存本次确认，跨页面刷新、APK 重启和多终端读取一致。
- 中控按房间设置关闭、观察、自动释放三种模式，以及全局暂停释放。
- 未确认超时释放、手动「提前结束」；提前结束先展示房间、会议时间和影响范围，再二次确认。
- 可查询的操作审计、失败告警和结果复核。

首版不包含推算官方签到码、写入飞书「已签到」、整场日程删除、会议改期、临时预约、人员身份核验、ESP 固件。重复会议在单次影响范围验证前不自动释放，也不开放提前结束。

## 2. 已核实的接口与待验证项

官方文档：[回复会议室日程实例](https://open.feishu.cn/document/server-docs/calendar-v4/meeting-room-event/reply-meeting-room-event-instance)。2026-09-20 已读取官方页面正文：

| 项目 | 文档内容 |
|---|---|
| 请求 | POST /open-apis/meeting_room/instance/reply |
| 权限 | calendar:room:readonly（获取会议室信息） |
| 应用类型 | 企业自建应用、商店应用 |
| 凭证 | tenant_access_token |
| 参数 | room_id、uid、original_time、status |
| 本版本使用的状态 | NOT_CHECK_IN、ENDED_BEFORE_DUE |

接口还列出 ACCEPTED_BY_ADMIN、DECLINED_BY_ADMIN；首版不调用，不能将「管理员接受」解释为「签到成功」。该接口无需 resource_token。

官方 [Pad 整合方案](https://www.feishu.cn/content/7271149634339618818)描述了未签到释放和提前结束。当前接口正文对 original_time 的说明为：普通日程和重复日程传 0，重复日程的例外日程传对应时间戳；旧方案却把重复日程传 0 描述为处理所有实例。此差异不能仅凭文档推断解决。

实施前必须通过以下验证：

1. 现有或独立应用的权限实际生效，能操作员工创建的测试预约；仅验证应用自己创建的日程不足以代表真实场景。
2. 非重复预约分别测试 NOT_CHECK_IN 和 ENDED_BEFORE_DUE，记录飞书忙闲变化、原日程表现、参与人通知以及同一日程其他会议室是否受影响。
3. 若引入重复会议，测试普通重复实例、改期例外实例，检查当前及后续至少两次预约；无法证明仅影响目标实例时保持禁用。
4. 飞书后台是否已有原生扫码签到和自动释放策略。未建立可靠的原生签到读取能力时，同一房间不得同时执行两套自动释放判断。
5. 超时、限流、重复提交和未知执行结果下的实际行为；正式业务不能依据 HTTP 200 单独认定释放成功。

当前忙闲快照没有可靠的重复规则字段，不能用 original_time=0 判断「非重复」。P0 必须验证如何取得足以识别日程类型的元数据；在自动识别落地前，写入测试只允许明确登记的非重复测试预约，不能仅凭房间白名单推广自动释放。

已知应用历史权限包含 calendar:room:readonly，但当前有效授权和释放结果尚未实测。测试需专门建立且明确允许释放的预约；当前计划不授权操作真实业务会议。

## 3. 产品规则（建议值）

| 规则 | 首版建议 |
|---|---|
| 默认模式 | 关闭；灰度房间先进入观察模式 |
| 可确认窗口 | 开始前 5 分钟至开始后 10 分钟；会议结束时终止 |
| 自动释放时点 | 开始后 10 分钟；会议已结束则不再补做释放 |
| 点击身份 | 持有效操作凭证的房间终端，表示现场设备确认，不证明某人到场 |
| 确认成功 | 以服务器持久写入成功为准；超时显示结果待核实并查询 |
| 配置生效 | 新加入监控的预约生效，不追溯释放已经开始的会议 |
| 预约改期或换实例 | 重新核验并提示重新确认；不能复用旧时间段的记录 |
| 无效或过期数据 | 禁止确认成功提示和自动释放，显示状态待核实 |
| 原生签到策略不明 | 允许只读展示，禁止该房间自动释放 |

观察模式明确显示「本次仅记录，不自动释放」。自动模式须清楚提示截止时间和未确认后果。对于继续使用官方二维码的房间，扫码结果仍以飞书页面为准；不能因为 RoomBeacon 没有点击记录就认定扫码用户未签到。

## 4. 交互与状态

正常路径：待确认 → 提交中 → 已确认使用；超时路径：待确认 → 到期待核验 → 释放处理中 → 已释放。

服务端返回可执行操作、截止时间及状态，前端不自行决定释放。提交错误显示明确原因；接口超时进入「结果待核实」，不把本地按钮点击当成成功。释放处理中禁止再次确认，并明确告知预约正在释放；点击与释放竞争由服务端原子状态转换决定先后。

「已释放」仅表示对应预约资源已释放，房间是否空闲仍由最新日程判断；若已有下一场或新的预约，不显示空闲。中控的预览功能保持只读，操作需进入明确的管理入口。

门牌显示系统内确认结果，不使用「飞书已签到」字样。首版不需要为业务按钮新增 Android 原生功能；在现有 WebView 和界面版本中复用组件，并验证 1280×800 横屏、触摸和刷新恢复。

## 5. 技术改动

### 服务端

保留现有终端缓存读取架构、API 路径、ROOM_DISPLAY_* 配置、rooms:* Redis 键与 argus_room_* 浏览器键。终端不直接调用飞书。

- 增加独立的确认与释放服务、飞书写操作封装及后台任务，不把写操作塞进现有采集循环。实现前补充 ADR，明确从只读展示扩展为受控写入的边界。
- 现有 GET /api/meeting-rooms/display 增加可选的 usage 状态；旧客户端忽略新字段即可继续展示。
- 拟新增 POST /api/meeting-rooms/usage/confirm、POST /api/meeting-rooms/usage/end 和 GET /api/meeting-rooms/usage/operations/{id}。操作接口先记录命令，由服务端任务执行与核验。
- 拟新增主控策略读取、更新和审计查询接口；全部校验主控凭证，终端凭证不得修改规则。
- 现有设备凭证严格限定 GET，不能直接放宽为任意 POST。新增单房间、限动作、可撤销的操作凭证；既有读凭证不自动获得写权限。操作能力按房间显式开通，凭证通过私有绑定流程交付，不放 URL 或日志。
- 房间身份取自凭证；服务端校验目标实例、版本、窗口和请求幂等键，拒绝跨房间、旧会议、旧版本和已撤销凭证。
- 原有飞书客户端对部分网络错误会重试；写操作应使用独立策略。网络超时后先复核结果，不沿用读取接口的盲目重试。

### 状态与持久化

在现有 Redis 内新增带版本前缀的数据，例如 rooms:usage:v1:*、rooms:usage-policy:v1:*、rooms:usage-audit:v1:*，不重命名旧键。

- 业务键至少包含 room_id、uid、original_time、实例开始时间；另外保存预约版本，避免同 uid 多次会议和改期误匹配。该键仅用于本地识别，不能替代飞书单次释放参数的验证。
- 保存确认时间、来源操作凭证标识、策略版本、截止时间、操作 ID、执行状态、脱敏错误码和复核结果；不存会议正文及原始凭证。
- 确认、到期入队和释放认领使用原子操作；任务设置租约，多进程去重。不能声称外部 API 与 Redis 组成完全原子事务。
- 首版复用 Redis AOF；上线前核查持久化配置并验证重启与恢复。记录缺失不等于未确认：只有完整登记、监控连续的待确认实例才允许进入释放候选。
- 服务重启、Redis 恢复或状态完整性不明时暂停自动释放，不追补中断期间错过的任务；重新获取目录和预约后，仅监控新的完整窗口。
- 审计建议保留 30 天，不含日程正文；确认与操作记录至少保留至目标实例结束后 7 天。实际留存配置在实施时确定。

### 后台释放任务

1. 检查全局开关、房间模式、当前策略版本、连续监控状态与设备心跳；失联、维护期间或短时恢复不自动释放。
2. 观察模式只记录「本会释放」及原因；自动模式才继续。
3. 通过服务端重新读取目标房间的最新上游预约，并再次校验实例、时间、确认状态；当前 300 秒采集快照不能单独作为写入依据。
4. 原子认领操作后调用指定状态；发送前再次检查暂停开关和任务有效性。上游没有条件更新接口时，保留并说明改期与释放并发的剩余风险。
5. 对业务成功响应重新查询忙闲，刷新缓存；仅目标时段可被确认解除占用时记录释放生效。网络超时或忙闲无法消歧时，进入结果待核实，不继续自动写入。
6. 失败保留预约显示依据并进入管理审计；按错误类型处理限流、权限撤销和原始时间失效，不用无限重试代替人工判断。

## 6. 实施阶段与通过条件

| 阶段 | 交付物 | 通过条件 |
|---|---|---|
| P0 接口验证 | 隔离测试预约、验证记录、权限与原生策略核对 | 普通预约的两种释放通过；影响范围与通知明确。失败则停止释放功能，仅保留展示方案 |
| P1 确认与观察 | ADR、持久确认、操作鉴权、门牌按钮、中控规则、观察任务 | 后端与浏览器测试通过；实机刷新、重启后状态一致；没有飞书业务写入 |
| P2 受控释放 | 写连接器、任务与复核、提前结束、全局暂停、审计 | 专用预约完成成功、失败、超时、并发和撤销测试；默认自动模式仍关闭 |
| P3 单房间灰度 | 部署与回退记录、现场验收记录 | 选北京 201 等明确批准的试点，先观察至少 3 个工作日且覆盖真实会议，再逐房间开启 |

P0 可先安排半天至一天；P1、P2 合计暂按 4–7 个工作日估算，取决于现有改动整合与接口行为。P3 的观察时间另计，重复日程问题不纳入首版交付承诺。以上为排期估算，不代表发布承诺。

## 7. 测试与验收

- 后端：有效确认、窗口边界、重复点击、伪造事件、跨房间、过期与撤销凭证、主控和设备权限隔离；更改时间、取消预约、会议结束、相同 uid 多次实例；确认与释放竞争、任务租约丢失、进程重启、Redis 恢复、写入丢失风险、配置中途切换。
- 外部连接器：成功、业务拒绝、权限不足、105003、401、429、5xx、畸形响应、请求已执行但响应丢失；失败不泄露凭证或上游正文。日常测试全部 mock 隔离。
- 前端：待确认、已确认、截止、断网、数据过期、提交失败、待核实和释放后新预约；控件重复操作、页面卸载清理、旧界面兼容、中控预览不可误操作。
- 实机：APK 重启、H5 更新、触摸操作、设备失联与恢复；真实接口与模拟测试分别记录。若 Android 源码有改动，另跑原生完整检查。
- 必跑：Ruff 0.16.7、pytest、frontend/npm ci、npm run build、npm test（Chromium）、git diff --check。原生改动时在 android/ 使用 JDK 17 / SDK 35 运行 ./gradlew testDebugUnitTest lintDebug assembleDebug。
- 自动释放验收：目标预约确实释放且可重新预约；不影响其他房间、其他会议或未来实例；飞书通知效果已确认；确认过的实例不释放，任何不确定状态均不误报成功或空闲。

## 8. 发布、回退与下一步

开发使用 codex/ 分支。当前工作区有其他功能未提交改动，实施前先整理基线和依赖，不把它们默认视为本计划的交付。按 P1、P2 拆分可审查变更；更新架构、交接、权限、运维文档和 CHANGELOG。

发布需明确准确 SHA、服务器目标、独立应用或借用应用、HTTPS 入口、Redis 持久化状态及回退步骤。新服务器由用户申请；不默认部署旧服务器，不从开发机复制源码，不推送 main。

回退顺序：关闭自动释放及提前结束 → 停止新增任务并核对在途操作 → 保存确认和审计记录 → 回退到展示版本。关闭开关不能撤销已发出的飞书请求；已经释放的预约不能靠代码回滚恢复，需先检查冲突再由管理员处理，不自动重新抢占房间。

建议下一步先启动 P0：确定一间测试会议室和明确可释放的非重复预约，验证两种释放操作；通过后才进入 P1/P2 实施。产品时间窗口先采用本计划建议值，在观察模式期间根据现场情况调整。
