## 1. 根因与正式交付目标

已通过真实接口确认：IT灯塔-Test固定配置来源日历A，10月9日13:00和10月10日09:00预约实际属于另一位组织者的主日历B。相同日程ID在A返回404／193001，在B返回200、起止时间完全匹配，并通过现有核验函数。应用具备这两场所需读取能力。证据见[排查记录](../docs/checkin-release-diagnosis-2026-10-10.md)。

实现缺口：房间被绑定到单一人的日历，没有按预约定位来源。测试缺口：现有自动核验fixture只配置一个日历，未覆盖不同组织者交替预约。运维缺口：实例核验失败最终使用release_not_enabled，不能直接区分开关未开与来源查错。交付缺口：单来源试点已启用容易被理解为任何人的预约均已可用。

正式交付目标：在明确的上线会议室范围内，普通员工分别创建的预约能够自动定位来源，签到后保留，符合释放条件且未签到时仅释放当前实例。用户无需逐人补配置或手动登记每场预约。正式使用涉及的共享日历、代订、应用创建和私密预约必须分别验证；无法覆盖的类型须作为明确的发布阻塞项或经用户确认的范围限制，不能悄悄算作通过。

## 2. P0：按预约解析来源，贯通释放前复核

### 2.1 来源证据和定位

1. 中央采集保留每个预约的组织者标识及证据时间，放在服务端私有数据中，与现有预约identity关联。终端仍只读取缓存，公共门牌响应不新增人员ID或原始日历ID。
2. 以真实忙闲记录中的组织者查询主日历，得到有依据的候选来源；批量、去重、限制并发并使用短期缓存。缓存按应用身份隔离，配置或身份变化使相关缓存失效。
3. 组织者主日历仅是候选。读取日程后核对event_id、organizer_calendar_id、状态、起止时间及重复实例；必要时沿返回的组织者日历定位权威来源，限制跳转数并拒绝循环、冲突和不完整证据。
4. 保留原单来源配置兼容，用于已批准来源及共享日历等有依据的补充候选。缺少组织者、应用身份或共享日历没有可验证来源时给出明确失败原因，不遍历全公司日历猜测，也不把某个候选返回200直接当成释放资格。
5. 日历证据必须与当前房间的唯一、有效忙闲实例一致。缓存过期、重叠、实例消失、时间改变或会议室被移除时停止授权；来源解析成功不代替房间写入白名单及其他释放条件。

实施涉及采集器、服务端来源证据、日历连接器和核验服务；必要时拆为单独模块，Python文件不超过500行。保留现有API路径、ROOM_DISPLAY_*配置、rooms:*键和预约identity，新增字段采取可选兼容方式；旧缓存缺少来源时等待可信新证据。

### 2.2 核验结果与发送前复核

每个实例保存已核验的来源依据、来源指纹、证据版本和重复释放范围。实际发送前读取同一已核验来源，重新核对日程及房间实例；来源发生变化须重新走核验，不能在发送阶段静默换来源继续发送。

原始来源ID仅供服务端解析与重查，公共响应和日志使用脱敏摘要。旧记录兼容原有固定映射；新增记录不能交给不认识来源格式的旧程序直接执行。

核验I/O结束后重查签到状态、页面回执、worker租约、策略及暂停，避免查询期间签到、改期或管理员暂停仍被释放。继续保持外部释放单次发送、超时不重试、真实读回后才显示成功。每日、每周、每月重复及改期例外均限定本次实例，禁止降级为整个系列的0实例释放。

与#61共用记录中已持久化的截止时间；核验重试、来源重新解析、前端刷新和重新采集均不能延长签到窗口。已有confirmed、blocked、uncertain等记录不批量重置或补授资格。

## 3. P0：失败分类与后台可诊断性

- 连接器提供稳定的内部错误分类，分别记录来源未解析、日程未找到、访问被拒绝、日程已变更、限流、网络超时、上游服务异常及响应不完整。只保留HTTP状态、数字业务码、允许的请求追踪号和脱敏实例／来源摘要，不输出原始响应、凭证或会议正文。
- 404／193001触发有依据的来源重新定位；对同一失败组合做短期负缓存并限制尝试次数。403不能靠重复请求解决；429遵循上游退避，超时及5xx使用有上限的退避。证据变化可重新尝试，所有读取仍受实例截止和总I/O预算约束，不能耗尽15秒释放前核验窗口。
- 后台分别显示“房间自动释放开关”和“本次预约释放资格”，显示最近成功／失败时间、具体原因及可执行处理提示；到期保护原因不得统一写成开关未启用。
- 来源核验失败在截止前进入后台异常列表，重复错误合并计数；截止时标明“预约已保留”和原因。门牌保留简短业务提示，管理员看到诊断细节。恢复必须由新的成功证据确认，不能仅清掉错误文案。

以上为后台可见异常与审计；邮件、IM通知或新的外部监控渠道不在本计划中自动启用。

## 4. P0：先复现再修复的回归矩阵

先增加会在旧实现上失败的用例：同一房间A和B两位组织者交替预约，A来源查B预约返回404，而B来源返回有效日程；新组织者C不能依赖预置名单。再实现修复，确认以下行为：

| 场景组 | 必须断言的结果 |
|---|---|
| A／B／C分别创建、同房间交替、相邻及跨日预约 | 正确来源各自独立，不串用上一场或另一房间的资格 |
| 来源缺失、不同应用身份、共享／代订／应用创建、私密预约 | 有真实依据才核验；不支持或不可读明确失败且不释放 |
| 候选返回200但ID／时间／权威来源不一致，多个冲突候选 | 拒绝错误证据，不以首个200作为成功 |
| 404、403、429、5xx、超时、分页不完整、畸形响应 | 错误分类准确，请求有界，无假成功、无敏感日志 |
| 缓存失效、组织者／来源变化、应用凭证轮换 | 不复用失效证据，不延长旧资格 |
| 非重复、每日／每周／每月重复、改期例外、仅显示单个重复实例 | 唯一本次实例；后续实例保持；范围不明时拒绝 |
| #61新增预约、固定截止、改期后重新签到、取消／移除房间 | 新实例独立核验，原期限保持，旧签到不继承 |
| 查询期间签到／暂停／撤销／改期；双worker竞争；写入超时 | 签到与释放仅一个胜者，外部写入最多一次，模糊结果不重试 |
| 重启、断网恢复、Redis记录丢失、旧保护、新旧记录共存 | 不把历史不确定性转成新释放资格 |
| 管理员与只读账号、终端响应、后台错误及恢复状态 | 权限边界正确，错误可定位，敏感字段不暴露 |

除了函数级mock，用接近真实脱敏结构的多来源HTTP fixture贯通“采集→来源定位→日历核验→状态机→释放读回”，防止只mock最终核验结果而绕过本次缺陷。补一条端到端验收脚本，分别输出预期、实际和证据位置。

必跑：Ruff 0.16.7、后端完整pytest（隔离Redis，零跳过）、前端npm ci／build／完整Chromium回归、git diff --check。增加多房间、多来源下的请求次数和总延迟检查，验证批量去重与缓存有效。Android源码若无修改沿用现有APK，另做真实设备业务验收；若改动原生则执行完整Android检查。

## 5. P0：真实验收与正式发布门槛

先在IT灯塔-Test受控试点，以原项目APK的真实门牌执行。实施前登记被授权的测试组织者、会议时段和预期写入范围；现有业务会议不作为强制释放测试。以下证据缺一项，不将“任意员工预约自动释放”标为正式可用：

1. **跨组织者**：至少3个真实员工账户，其中一个首次出现；每人至少完成签到保留和未签到释放各1场。6场均无需人工登记／改映射，记录真实日历来源摘要。
2. **变更与重复**：改期后重新签到、取消／移除会议室；每日、每周、每月及改期例外按实际支持范围验证只影响本次，独立确认后续实例仍在。
3. **来源类型**：实际正式使用的共享、代订、应用创建、私密预约逐类取样。来源覆盖表写清已验证、受限及待解决，普通员工预约不能再只覆盖一个人的日历。
4. **失败保护**：在隔离环境完成权限、网络、缓存、竞争和重启注入；在专用试点执行必要的实机断网／恢复验证。任何失败均不误报签到或释放成功，后台能明确定位原因。
5. **时效与一致性**：网络及上游正常、核验完成、心跳持续且符合释放条件的未签到预约，在服务器截止后30秒内完成释放和真实读回；达不到则分析处理。核对服务器审计、飞书独立读回与门牌状态三方一致，误释放、重复发送均为0。
6. **持续运行**：连续72小时覆盖工作时段、跨日及多组织者；安排实际有效场次，不能以“没有预约所以没有错误”通过。符合条件场次释放成功率100%，全部失败都有明确归因，无未解决的核心流程缺陷。

正式版的关键门槛是“受支持的真实业务场景通过”，测试条数和房间开关为true均不能替代这一条件。真实释放验收必须引用准确候选SHA；修复候选变化后重新验证受影响场景，不能沿用旧版本结果。

## 6. 发布与回退

实施顺序：失败回归 → 来源解析与错误分类 → 核验／状态机／后台集成 → 全量检查与代码审阅 → 单房间候选发布 → 真实矩阵及72小时观察 → 正式版放行。功能验收和发布审批分别留有证据，不能通过修改已有保护记录制造成功。

发布前重新读取生产准确SHA、房间范围、主控设备、规则及在途请求。09:12诊断基线为`9314125`，后续#61可能改变生产，不能把该历史SHA直接作为回退目标。记录PR／标签／准确SHA、配置差异、备份及回退命令，服务器从GitHub取得源码，检查通过后按明确发布授权部署。

按房间逐步启用新来源解析；读来源能力与会议室释放白名单分别管理。旧单来源配置继续兼容，不自动扩大其他房间写权限。先确认试点稳定，再逐批扩展。

回退先暂停相关释放并核对在途状态，再回退到兼容记录格式的版本。若旧版不认识新来源依据，回退后保持相关房间释放暂停；保留Redis／SQLite及后续业务记录，不整库恢复，不清seen／blocked／confirmed记录。部署失败、错误来源授权、重复发送或误释放立即停止扩展并执行回退流程。
